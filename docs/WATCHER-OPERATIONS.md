# Watcher delivery and timelock execution

The watcher reads confirmed Pocket events, forwards proposal/large-fill/execution notifications to an operator-configured receiver, and optionally pays for permissionless execution of a due change. Owner authorization and the timelock are enforced by the program. Revoking a session and cancelling a proposed change are separate owner actions. A notification is information to review, not permission to trade or change a pocket.

## Configuration

- `WATCHER_GENESIS_HASH`: independently approved chain identity; required.
- `WATCHER_STATE_PATH` and `WATCHER_STATE_KEY_PATH`: required durable SQLite queue/checkpoint path and a private file of exactly 32 raw encryption-key bytes. Legacy JSON is refused; preserve it for an independently checked migration.
- `RPC_ENDPOINTS_PATH` or `RPC_URL`: approved providers, as described in [RPC operations](RPC-OPERATIONS.md).
- `NOTIFY_WEBHOOK`: optional HTTPS receiver. Only local fixtures may use loopback HTTP. Without it, events are printed to the process console; that does not deliver them to an owner.
- `GHOSTLINK_WATCHER_KEYPAIR`: optional fee-payer file outside the repository. Omitting it disables execution of pending changes.
- `WATCHER_JOURNAL_PATH` and `WATCHER_JOURNAL_KEY_PATH`: required when a payer is configured. The first is a persistent SQLite path, the second a private file of 32 raw random encryption-key bytes. Keep both outside the repository, preserve the database and its WAL, and use the same database for every funded worker with this payer.
- `WATCHER_TOTAL_BUDGET_LAMPORTS`: explicit positive cumulative fee cap required for funded execution. This cap does **not** renew daily or reset on restart. Raising it requires an operator configuration change after reviewing prior spending. `WATCHER_MAX_FEE_LAMPORTS` defaults to 20000 and cannot exceed the total cap.
- `WATCHER_POLL_MS`: 100–30000 milliseconds, default 5000. `LARGE_FILL_USD_E6` defaults to 100000000 ($100).
- `WATCHER_PORT`: readiness/liveness HTTP port, falling back to `PORT` or 8791. Keep it behind operator network controls.
- `WATCHER_PAGES_PER_TICK`, `WATCHER_TRANSACTIONS_PER_TICK`, `WATCHER_DELIVERIES_PER_TICK`: defaults 4/32/32, maxima 100/1000/256. A page contains at most 1000 signatures.
- `WATCHER_TICK_BUDGET_MS`: default 10000, maximum 30000. This limits admission; an already admitted RPC, crank or receiver call finishes under its own transport deadline.

The entry point verifies the approved chain before starting. The same bounded HTTP pool performs polling, submission and confirmation; it never switches to an unapproved WebSocket provider. Startup and polling diagnostics omit raw provider/receiver exceptions and credentials. Importing the watcher class does not start a process or deliver notifications.

## State, delivery and retries

The encrypted checkpoint, in-progress scan and delivery records bind the genesis, Pocket program, payer/observer mode, alert threshold and receiver identity. The hosted receiver identity is a SHA-256 digest of its complete configured URL (or console mode); no receiver credentials are stored in queue metadata. Changing these settings, including URL credentials, requires a coordinated reviewed migration. Wrong keys/scopes and marked backup restore epochs are refused. Do not import a JSON cursor, reset state, change paths or restore an old copy to bypass missing history or replay warnings. Automatic migration, backup reconciliation and state-key/receiver rotation remain release work.

A fenced 90-second lease permits one state owner; hosted workers renew every 15 seconds and release it after draining. After a crash, wait for lease expiry. Stale owners cannot checkpoint or acknowledge after takeover. An external request already in flight can still reach its receiver after takeover, so the receiver must deduplicate; leases do not make HTTP side effects exactly-once. Separate database copies do not coordinate ownership. Host clock correctness and local durable storage are prerequisites.

Each scan captures one confirmed head slot and persists newest-first pagination. Newer signatures wait for the next scan. A saved cursor must appear in provider history; repeated pages, missing cursors, slot regressions, identity/status conflicts and incomplete/truncated logs stop advancement. All pages are staged before chronological delivery, preserving same-slot order. Bounded ticks resume their saved page position rather than gathering the entire backlog in a JavaScript array. Public signatures, slots and queue ordering are plaintext SQLite metadata; restrict the whole directory, database and WAL. Checkpoint/scan/lease/delivery records and queued observations use authenticated encryption scoped to the deployment and record identity. The protected remaining-count/ordinal detects deleted or reordered queued observations; changed public metadata is checked against its authenticated record. This does not authenticate the original RPC provider history.

Before contacting a receiver, the watcher commits the exact notification body, stable `eventId`, remaining alerts and candidate pending-change state. It durably acknowledges each successful response separately. After all alerts in a transaction are acknowledged, one FULL SQLite transaction commits the cursor/pending changes and dequeues the observation. A failed commit retains the old checkpoint; restart can finish an already acknowledged transaction without resending its alerts. A lost reply or crash before acknowledgment can redeliver the same body/ID. The receiver should atomically deduplicate `eventId` with its own durable handoff; HTTP success means receiver acceptance, not proof that a person saw the warning. There is no exactly-once delivery claim.

Notifications include `signature`, `observedSlot`, `observedCommitment: "confirmed"`, `genesisHash` and `pocketProgram`. Confirmed observations are provisional and may be orphaned; they are timely warnings, not finality certificates or authority to execute an action. If a saved cursor disappears on a fork or from pruned history, the worker stops and needs independent reconciliation. Finality reconciliation/retraction of earlier alerts remains a release gate. Bootstrap requires complete archival history; readiness is not proof that the provider returned every event. Receiver downtime blocks ordered progression and new crank admission while preserving prepared crank packets.

Webhook delivery has a 15-second deadline, refuses redirects and cancels unused response bodies. Each alert gets one admitted attempt per tick; failure retries its exact durable record on the next poll. Only connect a receiver approved to receive these events; test with synthetic/local receivers before contacting real users.

The queue defaults to at most 1,000,000 staged observations and twice that many scanned signatures. A derived pending snapshot holds at most 100,000 proposals and each encrypted state record is capped at 16 MiB. Transactions are limited to 2048 log lines, 64 KiB of logs and 256 decoded events/alerts. Capacity exhaustion refuses progress without discarding history. Pending snapshots are still materialized/serialized; crank-journal inventory, storage scaling, actual throughput and retention need pilot load/soak validation.

The shared event decoder follows the current PocketV3 `Filled` layout, including trade `mode` and `releasedCostUsdE6`. Truncated/legacy layouts and unsupported modes are refused. Indexed activity retains both fields. Large-fill alerts use the recorded input USD value; an unpriced speculative exit records zero input valuation, and its released historical cost must not be presented as current market value. This is not full strategy P&L monitoring.

Before funding a crank, the watcher requires fully acknowledged ingestion, renews state ownership and reads the current Pocket account through its approved provider. It checks program ownership, layout, PDA, current proposal and due slot. The encrypted journal is bound to genesis, program and payer. A SQLite FULL transaction saves the exact signed packet and reserves its quoted network fee atomically before broadcast. Write failure or an excessive/unavailable fee refuses the send. Two workers sharing that journal resolve to one packet and one reservation. Separate databases do not share a budget or transaction identity.

Retries and restarts reconcile the saved signature and can rebroadcast only its original bytes. The sender checks the packet's signature, payer and complete expected instruction message, compares the RPC acknowledgment and confirms only that locally known ID. A confirmed observation stops rebroadcast until finalized resolution or proven expiry; only actual successful `ChangeExecuted`/`ChangeCanceled` events clear pending notifications. A lost response does not authorize a fresh packet or refund the reserved fee.

A replacement for the same proposal requires absent signature history, finalized height beyond the saved expiry, a finalized invalid blockhash and the same proposal still present in a finalized Pocket account. Conflicting, stale or missing evidence retains the old attempt. At most three packets are prepared for a proposal, with a new conservative reservation for each; unused reservations are not automatically refunded. A finalized execution failure stops automatic retries of that proposal and requires operator investigation. Journal `confirmed` means signature inclusion is observed, not a successful owner alert; finalized failure has its own `failed` state. Do not delete records, switch database paths or restore old copies to reset spending. Backup rollback/reconciliation and coordinated key/payer rotation remain release work.

SIGINT/SIGTERM stops admission and waits for the active tick before closing storage and transport, with a 30-second forced-stop deadline. A forced exit leaves saved packets for reconciliation. `/ready` is 200 only for a current owner whose last completed scan and observed head advance are both under 30 seconds old, with no polling error or drain. Catch-up, stale head and delivery/storage failure return 503. `/health` is diagnostic liveness; neither endpoint proves user receipt, finalized history or successful crank settlement. Installed alerts, metrics, coordinated restore/rotation and hosted load/soak remain release gates. The candidate funded V2 watcher refuses known public mainnet/devnet genesis until a verified deployment migration is implemented.

## Verification

Focused tests additionally cover missing logs, repeated/missing pages, bounded pagination restart, actual SQLite rollback, stable IDs after a real HTTP receiver loses its reply, a child exit after a partial durable acknowledgment, competing state owners, cross-scope ciphertext substitution, readiness and actual Unix receiver-drain/restart. Tests also cover identical packets after lost/substituted acknowledgments, abrupt child exit after durable preparation, competing journal handles, atomic write failure, persistent fee caps, expiry evidence, packet instruction validation, active-work drain, scope refusal, backlog/restart, redirect refusal, streaming-response cleanup and import side effects. The service-process RPC drill starts the compiled watcher against wrong-chain/failing synthetic providers and verifies fallback, required funded configuration and private logs.

After building programs, circuits and the E2E dependency graph, run:

```sh
WATCHER_DRILL=1 bash scripts/localnet-e2e.sh
```

The disposable validator uses an explicitly synthetic mature pending account to test real compiled-program execution without waiting 24 hours, plus a future pending account that must remain untouched. This genesis state does not claim to prove owner consent. Separately, the ordinary E2E pocket uses real owner proofs to propose, revoke and cancel. The drill drops a crank acceptance reply at both the provider and watcher boundaries, checks identical fallback bytes, restarts the journal and compares the reservation with the actual payer debit. It also verifies actual PocketV3 trade alerts, fails execution-notification delivery and verifies recovery without a duplicate paid attempt or false execution alert. No public-chain upgrade or live-user notification is part of this test.
